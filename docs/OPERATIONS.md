# Operations

## Prerequisites

Required on the primary ARM host:

- Docker
- Docker Compose plugin or `docker-compose`
- Python 3
- a working OpenShell base install
- an existing frontdoor sandbox name, usually `nemobot`

Nemobot does not install the base cluster. It layers persistence, secret separation, worker delegation, browser/proxy containers, and the durable memory service on top.

## Recommended Install Flow

Initialize both frontdoor and worker state locally:

```bash
./stack-install.sh --init-state
```

Render and deploy the full stack:

```bash
export MODEL_BACKEND=codex-api
export OPENAI_API_KEY='<set-in-local-state>'
export MODEL_API_BASE_URL=https://api.openai.com/v1
export MODEL_API_PROVIDER_ID=openai
export MODEL_API_MODEL_ID=gpt-5.3-codex
export MODEL_API_MODEL_NAME=GPT-5.3-Codex
export WORKER_CODE_MODEL_ID=gpt-5.3-codex
export MODEL_CONTEXT_WINDOW=400000
export MODEL_MAX_TOKENS=32000
export SLACK_BOT_TOKEN='<set-in-local-state>'
export SLACK_APP_TOKEN='<set-in-local-state>'
export PERPLEXITY_API_KEY='<set-in-local-state>'
export PERPLEXITY_MODEL=sonar-pro
export TIMEOUT_SECONDS=2400
./stack-install.sh
```

`CODEX_API_KEY` is accepted as an alias for `OPENAI_API_KEY`; both mean an
OpenAI API key for API-backed inference.

For ChatGPT/Codex subscription auth, authenticate Codex CLI for the deployment
user and persist only the minimal CLI auth files:

```bash
codex login
./persist-codex-auth.sh
```

Then authenticate OpenClaw's Codex provider inside the running frontdoor sandbox
and persist that OpenClaw profile:

```bash
openclaw models auth login --provider openai-codex --set-default
./persist-openclaw-auth.sh
```

Deploy with an explicit backend selector:

```bash
export MODEL_BACKEND=codex-oauth
export CODEX_MODEL=gpt-5.5
./stack-install.sh
```

With `MODEL_BACKEND=codex-oauth`, the renderer pins agents to
`openai-codex/gpt-5.5` and ignores stale Anthropic/OpenAI API state. In `auto`
mode, the same route is selected when `state/openclaw-auth.tar` is present and no
API key/backend URL is configured. With `state/codex-auth.tar` present, the
frontdoor and workers can also run direct `codex exec` smoke tests. Use
`codex exec "prompt"` for non-interactive prompts; in the current Codex CLI, `-p`
selects a profile, not a prompt.

For local or third-party model serving, use the generic OpenAI-compatible route:

```bash
export MODEL_BACKEND=custom-openai
export MODEL_API_BASE_URL=http://model-api.example.internal:8001/v1
export MODEL_API_MODEL_ID=provider/model-name
export MODEL_API_KEY='<set-if-required>'
export WORKER_CODE_MODEL_ID=provider/model-name
./stack-install.sh
```

Anthropic Claude is also supported as a primary backend through OpenClaw’s native Anthropic provider. For this containerized deployment, the recommended subscription path is a Claude setup-token generated by `claude setup-token` on any machine and stored in ignored local state.

```bash
export MODEL_BACKEND=anthropic
export ANTHROPIC_AUTH_MODE=setup-token
export ANTHROPIC_SETUP_TOKEN='<set-in-local-state>'
export ANTHROPIC_MODEL=claude-opus-4-7
export WORKER_CODE_MODEL_ID=claude-opus-4-7
./stack-install.sh
```

Anthropic API keys still work as a fallback:

```bash
export MODEL_BACKEND=anthropic
export ANTHROPIC_AUTH_MODE=api-key
export ANTHROPIC_API_KEY='<set-in-local-state>'
export ANTHROPIC_MODEL=claude-opus-4-7
export WORKER_CODE_MODEL_ID=claude-opus-4-7
./stack-install.sh
```

If you want the installer to prompt for deployment-specific values instead of exporting env vars manually, run:

```bash
./bootstrap.sh
```

The primary inference backend only needs to expose a compatible model-serving API. The tracked code still accepts legacy environment aliases for backward compatibility, but the documented interface is generic.

`MODEL_BACKEND` accepts `auto`, `codex-oauth`, `codex-api`, `custom-openai`, and `anthropic`. Explicit values win over persisted auth bundles, so switching from Codex OAuth back to Anthropic no longer requires moving `state/openclaw-auth.tar` aside.

`WORKER_CODE_MODEL_ID` controls the worker-side analyzer and verifier model. It must support OpenClaw tool use on your proxy path. The preferred API-backed default is `gpt-5.3-codex`; the preferred subscription-backed default is `gpt-5.5` when using the same `openai-codex` provider.

For long-running analyzer or verifier tasks, use the async worker bridge flow:

```bash
openclaw-bridge submit --agent analyzer --session firecracker-a --query-file prompt.txt
openclaw-bridge wait --job x86:<job-id> --timeout 900
```

For guest-boundary or boot/runtime checks that need more than a disposable container, use the x86 lab VM plane:

```bash
curl -fsSG 'http://lab-control.openshell-lab.svc.cluster.local:8090/vm/run' \
  --data-urlencode 'image=ubuntu-24.04' \
  --data-urlencode 'name=vm-check' \
  --data-urlencode 'script=uname -a; id' \
  --data-urlencode 'timeout=900' \
  --data-urlencode 'memoryMiB=2048' \
  --data-urlencode 'vcpus=2'
```

For an in-place rebuild/update of an existing deployment, use:

```bash
./reinstall.sh
```

`reinstall.sh` preserves the durable memory Docker volume by default and writes a timestamped SQL backup when `openclaw-memory-db` is running.

`release.env` is the source of truth for the packaged OpenClaw release,
official external plugin versions, and the pinned stable OpenShell images.
Rebuilds pass the OpenClaw pin into both sandbox images, local and remote
cluster resets consume the OpenShell image pins, and frontdoor startup
re-syncs the Slack plugin in `~/.openclaw/npm` if it has drifted away from the
host OpenClaw release.

`stack-install.sh` does three things in order:

1. deploys the frontdoor sandbox and host-side Docker containers
2. deploys the worker sandbox
3. deploys the in-cluster worker bridge

## Individual Entrypoints

Use the individual scripts when you only want to touch one layer.

### Frontdoor only

```bash
./install.sh
```

### Worker only

```bash
./arm-worker/install.sh
```

### Bridge only

```bash
./bridge/install.sh
```

### x86 lab worker

```bash
./x86-worker/install-remote.sh
./x86-worker/install-bridge.sh
```

## Refreshing Live State

Refresh the frontdoor config and workspaces from a running sandbox:

```bash
./install.sh --refresh-live-config
```

Refresh the worker from its own running sandbox:

```bash
./arm-worker/install.sh --refresh-live-config
```

For the worker, this refreshes workspace files from the running sandbox, but `arm-worker/state/openclaw.json` is still re-rendered from the worker template plus shared frontdoor model/search settings. That is intentional. The worker config should not drift by inheriting frontdoor runtime state.

Refresh the whole stack with the wrapper:

```bash
./stack-install.sh --refresh-live-frontdoor --refresh-live-worker
```

## Naming Migration

Fresh tracked defaults use:

- `openshell-cluster-nemobot`
- `openshell/sandbox-from:nemobot`
- `/opt/openclaw-nemobot`

Legacy deployments may still be on:

- `openshell-cluster-nemoclaw`
- `openshell/sandbox-from:vulnlab`
- `/opt/openclaw-vulnlab`

The install and entrypoint scripts keep compatibility fallbacks for those older names so you can update an existing deployment before you finish renaming its live runtime objects.

## Expected Secret Placement

Keep secrets in env files or Kubernetes secrets, not in prose docs and not as literal values in `openclaw.json`.

- Slack tokens: `state/runtime.env`
- Anthropic setup-token or Anthropic API key: `state/model-auth.env`
- NVIDIA key: `state/nvidia-proxy.env`
- Perplexity key: `state/perplexity-proxy.env`
- Postgres credentials for memory service: `state/memory-service.env`
- gateway tokens: rendered into each sandbox config or the bridge env secret

## Safe Reinstall / Update

For an ARM-only rebuild that preserves durable memory:

```bash
./reinstall.sh
```

For a primary ARM rebuild plus x86 worker update:

```bash
./reinstall.sh --with-x86-worker --remote-host x86-worker.example.internal
```

For a destructive x86 lab cluster reset during update:

```bash
./reinstall.sh --with-x86-worker --remote-host x86-worker.example.internal --reset-x86-cluster
```

Notes:

- `reinstall.sh` does not remove the `openclaw-memory-db-data` Docker volume.
- If the memory DB is running, it writes a SQL backup under `backups/<timestamp>/openclaw-memory.sql` first.
- It updates the x86 worker host by rerunning `x86-worker/install-remote.sh`; the frontdoor-host x86 bridge is refreshed in the same run unless `--skip-bridge` is set.

```bash
docker exec openshell-cluster-nemobot kubectl exec -n openshell nemobot -- openclaw channels status --json
```

- Slack channel account is `running: true`
- frontdoor config shows proxy URLs for NVIDIA and Perplexity, and canonical `anthropic/...` model refs when native Anthropic auth is enabled
- frontdoor config shows `${SLACK_BOT_TOKEN}` and `${SLACK_APP_TOKEN}`

### Worker sandbox

```bash
docker exec openshell-cluster-nemobot kubectl exec -n openshell nemoworker -- openclaw status --json
docker exec openshell-cluster-nemobot kubectl exec -n openshell nemoworker -- openclaw channels status --json
```

What matters:

- worker gateway is reachable
- worker channel list is empty
- worker built-in memory still exists for local scratch state
- durable memory service should be reachable on `http://host.openshell.internal:9004`
- worker agent ids should be `main`, `researcher`, `analyzer`, and `verifier`

### Vulnerability-research frontdoor path

After deploy, the intended live flow is:

1. Slack reaches `communicator`
2. `communicator` classifies vulnerability-research work and spawns `vuln_researcher`
3. `vuln_researcher` does quick source discovery with `web_search` and `web_fetch`
4. `vuln_researcher` spawns `orchestrator` for code checkout, bridge calls, VM work, or durable-memory writes
5. `orchestrator` uses `openclaw-bridge` and `openclaw-memory` for private bridge and durable-memory actions
6. `researcher`, `analyzer`, and `verifier` run in worker sandboxes, not in the Slack-facing frontdoor

## Troubleshooting

### Frontdoor pod comes up but Slack is silent

- check `openclaw channels status --json`
- confirm the Slack account is `running: true`
- confirm the frontdoor config still contains env references for the Slack tokens

### Worker comes up but shows a Slack section in config

That can happen because `openclaw doctor --fix` backfills default channel shape. The important check is still:

- `openclaw channels status --json` returns no configured channels
- worker config has `channels.slack.enabled = false`
- worker config has `plugins.entries.slack.enabled = false`
- worker config should not reference `openclaw-env-nemobot`
- worker pod `envFrom` should be empty unless you explicitly introduce a worker-only secret

### Worker direct `GET /v1/models` returns HTML

That is not by itself proof that the worker gateway is broken. Use:

- `openclaw status --json`
- a real `POST /v1/chat/completions` call
- or the bridge health and run path

### Browser opens but page actions fail

- verify `openclaw-cdp-browser` is running
- from a sandbox, verify `http://host.openshell.internal:9223/json/version`

### Provider calls fail

- verify the host proxy containers are up
- verify the corresponding env file exists on the primary ARM host
- verify OpenClaw config still points at `host.openshell.internal:9002` or `:9003`

### Public GitHub work is flaky or rate-limited

- prefer plain HTTPS clone for code checkout
- use `https://api.github.com/repos/<owner>/<repo>` for structured public metadata
- avoid assuming any GitHub token exists in the worker sandboxes

### x86 lab jobs fail to launch

- verify `lab-control` is healthy in namespace `openshell-lab`
- verify the requested profile exists
- inspect job list with `curl http://lab-control.openshell-lab.svc.cluster.local:8090/jobs`
- inspect logs with `curl http://lab-control.openshell-lab.svc.cluster.local:8090/logs?name=<job-name>`

### Memory service calls fail

- verify `openclaw-memory-db` and `openclaw-memory-service` are running
- verify `state/memory-service.env` exists on the primary ARM host
- verify `curl "http://${HOST_GATEWAY_BIND}:9004/healthz"` works on the primary ARM host
- verify sandbox access with `curl http://host.openshell.internal:9004/healthz`
- remember that `web_fetch` will block `host.openshell.internal`; internal memory-service access should use `curl` from `vuln_researcher`, `orchestrator`, or worker agents

## Security Notes

- the frontdoor sandbox is the only place that should see Slack credentials
- the worker sandbox should not receive Slack or provider API keys
- host helper services should stay as dedicated containers
- avoid mounting host Docker or host `/root` into any sandbox
- if you add a secondary x86 worker host, keep it as a separate build and validation plane, not a Slack-facing endpoint
